# Panier v2 — signed key-delivery confirmation (experimental)

**Prototype. No production Worker, protocol endpoint, UI, or membership change.
Independent security review is required before use.**

## Motivation

The signed QR join in PR #23 authenticates a member's *ECDH public key*
under their signing identity. That does not prove the device still possesses
the non-extractable ECDH private key or actually recovered the new list secret
after a revocation.

A correct key-delivery confirmation must establish that the active member
can decrypt a specific owner-signed key package for a specific membership
epoch and rotation head, and that the confirmation was made with the **same
member signing key** registered in the verified membership history.

## Candidate design

The `v2/rekey-receipt.mjs` module implements two interfaces:

- `receiveAndConfirmRekey`: client checks the caller-supplied, already
  **cryptographically verified** membership state, including list, epoch,
  member, owner and rotation head. It verifies the owner's signed key package
  and decrypts it using the recipient ECDH private key (PR #22). The
  recipient signs a receipt and includes a 256-bit HMAC confirmation tag
  derived from the **fresh decrypted epoch secret** via domain-separated
  HKDF-SHA-256. The tag authenticates a canonical transcript containing
  list, owner, recipient, epoch, rotation head, and SHA-256 of the **exact**
  owner-signed encrypted package.
- `verifyRekeyReceipt`: the owner compares the envelope and its previously
  verified membership checkpoint, verifies the signature against the member's
  **registered signing key**, then verifies the secret-derived HMAC tag using
  the fresh epoch secret generated by the owner. The verifier returns a
  narrow `{confirmed:true,...}` result for that specific recipient and
  package only.

This prevents the server from fabricating successful delivery receipts:
it possesses neither the member signing private key nor the fresh epoch
secret. Reusing a legitimate receipt for another key package or epoch
fails because the transcript binds the precise signed package and rotation
head.

**Important limitation:** the proof establishes that the registered signing
identity **knows** the new secret. It is not a mathematical, unconditional
proof of possession of the ECDH private key if the secret was disclosed by
another channel. The recipient's successful decrypt operation is part of
the intended client flow, but the server does not witness that operation.

## What the caller must already trust

- Owner genesis public-key pinning and entire signed membership history from
  PRs #21/#23. Checking a server-supplied materialized membership object
  without signature verification is **not sufficient**.
- A previously pinned head or freshness/consistency mechanism to prevent
  a malicious server withholding a later revocation. The current code checks
  an expected head, but **does not produce independent freshness evidence**.
- A legitimately owner-signed package for the new epoch and exact recipient,
  and the authentic registered recipient signing public key.
- A locally generated fresh content secret. A stolen QR or an old ciphertext
  does not become confidential retroactively by issuing a receipt.

## Still missing before production

1. **Atomic epoch publication:** owner-signed membership rotation,
   recipient-specific wrapped secrets, and the new-epoch append fence must
   become a single consistent server transition; no partial-key cutover.
2. **Durable receipts and lost-response retries:** this PR does not persist
   receipts. The transport must support safe, idempotent receipt submission
   and retrieval, keyed by list, member, epoch, rotation head and package hash.
   A network timeout must not be interpreted as failed decryption.
3. **Offline surviving devices:** one recipient can confirm promptly but
   others may be offline. A key-delivery policy must distinguish
   prepared/available/confirmed and avoid blocking the list indefinitely.
4. **Recovery and revocation:** owner kit/transfer, stale offline mutation
   rebasing, old-epoch append rejection and equivocation remain security
   review gates in PR #12.
5. **Key lifecycle:** do not log, export, sync to analytics, or copy raw
   epoch secrets to Cloudflare. Local plaintext and non-extractable
   CryptoKeys are still exposed to compromised same-origin JavaScript.
6. **Cryptographic interoperability:** this is a candidate canonical JSON
   transcript with P-256 ECDSA and Web Crypto HMAC/HKDF; cross-browser
   cryptographic vectors and independent protocol analysis remain required.

## Tests

`node --test test/v2-rekey-receipt.test.mjs` covers valid confirmation,
forged signatures, wrong/missing fresh secret, wrong ECDH private key,
wrong recipient signing key, revoked identity, altered exact ciphertext,
another epoch/head, malformed wire fields, and repeated receipts.

All tests run locally using Web Crypto and synthetic identities; no real
Durable Object or deployment is involved. The v1 app and Raspberry Pi/Go
code remain unchanged.
